# M2.6 — MODE (SERVING / SETTING)

**Status:** planned, not built. Written 2026-08-11. Implement in the next session.

**Read `docs/HOTPOT_ARCHITECTURE_v3.md` §9.1, §12.2, §14.5 first.** This plan
extends that doc; it does not replace it. The doc edits listed in build item 11
are part of *this* implementation and have NOT been made yet — until they are,
§9.1 still says "staff mode" and is still ground truth for everything except
what this file supersedes.

---

## 1. WHY THIS COMES BEFORE M3

The doc never gave the mode its own milestone. `fsm.py`'s docstring claims M2
and M7 give STAFF something to do; M2's build items (§21) never mention it, and
M7 build items 3–4 are the first that functionally need it. So the state was
scheduled to arrive five milestones after the first thing that depended on it.

That gap is already visible in the code, in three places:

- **`core/main.py`'s `_state_msg()` hardcodes `"mode": "diner"`** with a comment
  apologising for it. Doc §4.3 has specified a `mode` field since v3.0 and
  nothing has ever produced it.
- **`Core._calibrating` + `CAL_FREEZE_TIMEOUT_S`** (added M2.4, extended in
  commit `3a1ee6f`) is a per-bin "do not bill this bin" freeze. It exists
  *only* because there is no mode-wide "not billing" state. It is the local
  workaround for the missing global one, complete with its own dropped-tablet
  timeout.
- **`binmap.locked`** exists, is persisted in `state/bin_map.json`, is loaded
  back, and **nothing has ever set it.** Its one writer in §9.1 is staff-mode
  exit.

Every milestone from here branches on the mode: M4's calibration wizard is a
setting-mode activity (§3.2 says so outright), M5's hover must be inert while
staff hands are over the table, M6's checkout shares `reset_session()`, M7 is
built entirely on enter/exit, M8 renders the visual difference. Building it now
means M4–M8 are written against a mode that exists, instead of each inventing
its own gate the way M2.4 already had to.

The rename is also cheapest now, purely on prose grounds: M4–M9's milestone text
is not yet written against any vocabulary, so it will be written in the new one
rather than edited into it later.

## 2. DECISIONS — SETTLED, DO NOT REOPEN

| # | Decision | Rationale |
|---|---|---|
| 1 | Modes are **`SERVING`** and **`SETTING`** | See §3 below |
| 2 | The **Setup tab** (§12.6) keeps its name | It is a quiet tab label with 4 doc mentions; the mode is the loud concept and needed the distinct word |
| 3 | **"Staff view" keeps its name** | It is a *surface* (the tablet), used in both modes. Not renaming it is the entire point of renaming the mode |
| 4 | Tare and Calibrate are **gated behind `SETTING`** | §12.4's flow requires an empty bin and a reference mass — both are picks in serving mode |
| 5 | Banner precedence: **`SETTING` wins over `error`** | See build item 9 |

### 3. Why `SERVING` / `SETTING`

The old names — `diner mode` / `staff mode` — name **who is standing at the
table**. That is the wrong noun. Staff are present in both modes; a diner can
walk up during either. What actually differs is **what the table is doing**:
billing, or being changed.

`staff mode` additionally collided with `staff view` (40 doc mentions), the
tablet UI, which is used in *both* modes. That collision was the concrete cost
of the old name and is what the rename buys back.

`SETTING` was chosen over `SETUP`, `PREP`, `MAINTENANCE` and `OPERATOR`:

- **`SETUP`** — collides with the Setup tab (§12.6).
- **`PREP`** — genuine restaurant vocabulary ("prep cook", "prep list"), but it
  names only one of the four activities this mode covers (filling trays). Load-cell
  calibration, dot calibration and dataset capture are not prep. Prep also
  happens in the kitchen before opening; this table is on the dining floor.
- **`MAINTENANCE`** — accurate but reads as infrastructure, not food service.
- **`OPERATOR`** — matches the doc's own word for the tablet user, but pairs
  badly with `SERVING`: one is a gerund, one is a person.
- **`SETTING`** — *setting the table* is the food-service idiom for exactly this
  work. Pairs with `SERVING` as a matched gerund before/during arc, reads plainly
  to an operator or a judge (§12.1's no-jargon rule), and shares no literal
  string with `Setup`, `staff view`, or the `Live` tab.

Residual weakness, accepted: `SETTING` and `Setup` remain near-synonyms, so a
faint conceptual overlap survives even though the literal collision is gone.
Judged acceptable — "the Setup tab is open while in SETTING mode" reads fine.

## 5. BUILD

### 1. `core/fsm.py` — the state

Add `State.SETTING`. Two transitions, per §9.1:

```
any ──(enter setting, cart not active)──► SETTING
SETTING ──(exit setting)──► IDLE   [refresh weights, re-baseline, lock bin map]
```

`enter_setting()` must be **refusable with a reason**, not just `False`. §9.1:
*"The staff view shows why it is refused and offers 'cancel the order first.'"*
`_go()`'s bool return cannot carry that. Add:

```python
def can_enter_setting(self) -> Optional[str]:
    """None if allowed; otherwise a plain-language reason (§12.1)."""
```

`enter_setting()` calls it and refuses on a non-None result.

### 2. `core/cart.py` — what "cart is active" means

`Cart` has no such predicate. Add `is_active()`:

```python
return any(g > 0.0 for g in self.shown_g)
```

**`shown_g`, NOT `removed_grams()`.** This is the single most likely thing to be
got wrong here. `removed_g = max(0, start_g - live_g)` is raw and moves with
load-cell noise — CLAUDE.md's own per-channel table has four bins at 500–1500
counts rms, which at a plausible counts/gram is several grams of permanent
wobble. Using `removed_g` would make `is_active()` true essentially always on a
noisy channel and **setting mode would be permanently unreachable.** `shown_g`
is deadband-gated, so it is 0 until a real ≥10 g pick lands, and it is also
exactly what the diner can see on the table — refusing on something visible is
explicable to an operator; refusing on invisible noise is not.

Accepted cost: a sub-deadband pick (say 5 g) reads as inactive and is discarded
by the re-baseline on entry. That is ~₹0.60 and invisible on the table. Weigh
that against a mode that cannot be entered at all.

### 3. `core/fsm.py` — exit sequence, and the trap in it

`exit_setting()` must do three things in this order, all inside Fsm so no caller
can do two of them and forget the third (the same argument `fsm.py`'s docstring
already makes for `reset_session()`):

1. **Refresh `live_g` from the scale for every bin.**
2. `cart.reset_session()`.
3. Lock the bin map.

**TRAP — step 1 is not optional and is easy to miss.** `_apply_scale_to_cart()`
is disabled during SETTING (build item 4), so by the time exit runs, `live_g`
still holds whatever the bins weighed when setting mode was *entered*.
`reset_session()` does `start_g[i] = live_g[i]`. So if staff swap a full tray
for an empty one during setting mode — which is the entire point of the mode —
exit would set `start_g` to the **old full tray's weight**, and the next state
tick would set `live_g` to the new empty weight. `removed_g` becomes the whole
tray and the next diner is billed for the swap.

This is the same hazard `_handle_cal_session`'s `cal_end` already solves per-bin
with `cart.seed_live_grams()`. Exit is the eight-bin version of it.

Fsm has no scale. Wire it the way `on_transition` is already wired: a
`refresh_weights: Callable[[], None]` passed into `Fsm.__init__`, called as step
1. Core supplies a closure that reads `scale.read()` and calls
`cart.seed_live_grams(i, g)` for every bin with a non-`None` reading. Bins the
scale cannot weigh keep their mock/placeholder value, same rule as everywhere else.

Fsm also needs the `BinMap` for step 3 — take it in the constructor alongside
`Cart`, for the identical reason: "exit locks the map" is only a guarantee if it
cannot be bypassed.

### 4. `core/main.py` — billing gated by mode

`_apply_scale_to_cart()` returns immediately when `fsm.state is State.SETTING`.
This is the whole point of the milestone: staff lifting a tray is not a pick.

`_state_msg()`'s hardcoded `"mode": "diner"` becomes derived:
`"setting" if fsm.state is State.SETTING else "serving"`. Delete the apology
comment with it.

### 5. `core/main.py` — delete the `_calibrating` workaround

With build items 3 and 4 in place, `Core._calibrating`, `CAL_FREEZE_TIMEOUT_S`,
`_handle_cal_session`, and the `cal_begin`/`cal_end` wire messages are all dead:

- Tare/Calibrate now require SETTING (decision 4), and
- in SETTING, `_apply_scale_to_cart()` does nothing at all, and
- exit re-baselines all eight bins, which is what `cal_end` did for one.

Delete all of it, plus `index.html`'s `cal_begin`/`cal_end` sends. The tests that
die with it are in `test_core_main.py` — the wizard-freeze cases from commit
`3a1ee6f`. Their *intent* survives as the new "scale frozen in SETTING" test
(build item 10), so replace rather than simply drop.

Removing code is the signal that the mode is the right abstraction. If this
deletion turns out not to be clean, stop and re-read build item 3 — something
has been missed.

### 6. Wire protocol — two new messages

Tablet → core:

```json
{"t":"set_mode","mode":"setting"}
```

Core → tablet, broadcast **on change, not on a timer** (same model as
`_on_pip_change`; no new clock):

```json
{"t":"mode","mode":"serving","cart_active":false,"refused":null}
```

`cart_active` lets the action bar pre-warn without a round trip, so broadcast
whenever *either* field flips. `refused` carries `can_enter_setting()`'s reason
on a rejected `set_mode` and is `null` otherwise.

Reply is a **broadcast, not a direct answer to the asking tablet** — `on_message`
hands the callback the decoded frame with no connection handle (`server.py`'s
docstring). That is correct here rather than merely tolerated: mode is global
state and every attached tablet must agree on it.

### 7. `web/server.py` — `on_join` must send more than one message

Today `on_join` returns exactly one object and `Server._handle` sends it once
(`server.py:209`). Core passes `_pips_msg`. A tablet opening the page needs both
the pips **and** the current mode, or its action bar renders wrong until someone
touches something.

Change `on_join` to accept a single object **or a list of objects**, sending each
in turn. Small, backward-compatible (`test_web.py:138`'s single-object case must
keep passing), and the Bins tab will want the same thing later.

### 8. Staff view — the toggle

§12.2's action bar does not exist yet. Build it: fixed to the bottom, above the
developer panel, on every tab.

```
┌──────────────────────────────────────────────────┐
│  [ ENTER SETTING MODE ]        [ Cancel order ]  │
└──────────────────────────────────────────────────┘
```

- **One primary button that names what happens next** — `ENTER SETTING MODE` /
  `EXIT SETTING MODE`. Not a two-position switch: §12.1 is "one primary action
  per screen", and a switch invites a mis-tap into the one transition that
  destroys a diner's order.
- **When refused, the button stays tappable and explains.** Do not disable it
  silently. Tapping with an active cart shows `refused` verbatim plus a
  "Cancel the order first" action wired to `Cancel order`. §9.1 asks for exactly
  this pairing.
- `Cancel order` wires `fsm.cancel()` — which exists in `fsm.py` and has never
  had a caller. Confirmation required before it fires (it re-baselines).
- Header `#mode` (currently the literal `—`) shows the live mode: neutral in
  serving, **amber** in setting, matching the table's amber chrome per I8.

### 9. oF — the banner

`UiLayer::drawErrorOverlay()` already draws a 72 px top-edge strip and was built
explicitly on §14.5's banner pattern (see CLAUDE.md, 2026-08-11). Generalise it
to take colour and text, then add the setting-mode case: amber fill,
`SETTING — NOT BILLING`.

**Precedence — `SETTING` wins over `error`.** Both claim the same strip and both
can be true at once (in setting mode, someone knocks the XIAO cable out). In
SETTING nothing bills — `_apply_scale_to_cart()` is off — so
`SCALES OFFLINE — NOT BILLING` is warning about a risk that cannot occur. The
person doing setting-mode work is holding the tablet, and the Bins tab already
shows `Load cells: no connection`; the table banner is for everyone *not*
holding the tablet.

Establish this as a general rule now, in the doc, because `calibrating` (M4) and
`recap`/`qr` (M6) will each ask the same question.

The rest of §14.5 — fluid off, amber chrome, the 100 mm grid — stays M8's. Most
of it is a no-op today since no fluid exists. The banner alone is what makes
this milestone's acceptance test visible from across the room.

### 10. Tests

Every one must be checked capable of failing by reverting the thing it covers.

- `enter_setting()` refused with an active cart, and the reason string reaches
  the wire.
- `enter_setting()` allowed with sub-deadband weight present (the `shown_g`
  decision — mutate to `removed_grams()` and watch it go red).
- **Exit re-baselines against *current* weight, not stale.** Drive it as the real
  scenario: enter setting, change a bin's scale reading by ~400 g, exit, assert
  `picked` is 0 on the next `_state_msg()`. **This is the build-item-3 trap; if
  only one test is written for this milestone, write this one.** Mutate by
  removing the refresh step and confirm a phantom ~400 g pick appears.
- Exit sets `binmap.locked`.
- Scale readings do not reach Cart while in SETTING.
- Mode appears correctly on the `state` message in both modes.
- Full toggle round-trip over a real WebSocket (`test_web.py` /
  `test_core_main.py` already have this pattern from the Bins tab).
- Tare and Calibrate refused while in SERVING.
- `on_join` returning a list sends every message; returning a single object
  still works.

## 6. ACCEPTANCE (human, on the rig)

- Tap `ENTER SETTING MODE` with an empty cart → header chip goes amber, the
  table shows the amber banner, and it is unmistakable from three metres.
- Pick ~50 g from a bin, then tap `ENTER SETTING MODE` → **refused**, with a
  readable reason and a working "Cancel the order first".
- In setting mode, lift a whole tray out and put a different one back → the
  total does not move and no pick is registered.
- Exit setting mode → **the total is 0 and stays 0.** This is the trap in build
  item 3. If a large phantom pick appears here, the weight refresh is missing.
- After exit, `state/bin_map.json` has `"locked": true`.
- Tare and Calibrate are unreachable in serving mode and work in setting mode.
- Unplug the XIAO while in setting mode → the banner still reads
  `SETTING — NOT BILLING`, not the scales-offline banner.
